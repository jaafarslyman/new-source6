6. Issue Relationships

Use proper relational database relationships.

An issue should reference:

- Company/workspace
- Contact
- Property
- Unit
- Service
- Assigned staff

These should be UUID foreign keys to the existing records.

Do NOT store:

- property names
- unit names
- staff names
- service names
- contact names

as the primary relationship mechanism.

Use foreign keys.

All relationships must respect the existing company/workspace isolation.

For example, a company must not be able to create an issue belonging to a contact/property/unit/staff member/service from another company.

15. RLS / Security

Use the existing FlowPoint multi-tenant architecture.

Every issue and issue activity must be isolated to the correct company/workspace.

RLS must prevent users from:

- Reading another company's issues
- Creating issues linked to another company's contacts/properties/units/services/staff
- Updating another company's issues
- Deleting another company's issues
- Creating cross-company issue relationships

Do not invent a new authentication or tenancy system.

Inspect and reuse the existing one.
