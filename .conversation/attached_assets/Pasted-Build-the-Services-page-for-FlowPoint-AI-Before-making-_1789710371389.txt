Build the Services page for FlowPoint AI.

Before making changes, inspect the existing project, database integration, Supabase schema, navigation, and the recently built Properties, Units, Contacts, and Team/Staff pages. Reuse the existing FlowPoint design system and architecture. Do NOT redesign the application.

1. Services Page

Create a dedicated "/services" page and add Services to the existing navigation.

The page should manage the company's services/offerings and act as the structured source of truth that the AI will later use when understanding what the company provides.

Use the same:

- Typography
- Colors
- Spacing
- Buttons
- Cards
- Icons
- Modals
- Form styling
- Responsive behavior
- Navigation
- Empty states
- Loading states

as the existing FlowPoint UI.

Do not introduce a new visual style.

2. Services List

The main page should display services in the same polished style as the other management pages.

Each service should show:

- Service name
- Category
- Short description
- Status: Active / Inactive
- Number of contacts using the service
- Number of properties/units associated with it
- Assigned staff/team
- Last updated

Include:

- Search by service name/category
- Filter by category
- Filter by status
- Add Service button

All filters/dropdowns must use FlowPoint's custom dropdown UI.

Never use native HTML "<select>" elements.

Create a polished modal for adding and editing services.

Organize the form into logical sections.

Basic Information

- Service name
- Category
- Short description
- Detailed description
- Status: Active / Inactive

Operations

- Assigned staff/team members
- Properties the service applies to
- Units the service applies to
- Availability / eligibility
- Typical response time

Customer-Facing Information

- Customer-facing description
- Requirements / eligibility
- What is included
- What is not included
- Pricing / fee information (optional)
- Important customer-facing policies

Do not force pricing fields if a service does not have a fixed price.

Use proper relational data for staff, properties, and units rather than storing names as comma-separated text.

5. Database

First inspect the existing Supabase schema.

If a "services" table already exists, reuse and extend it instead of creating a duplicate table.

If it does not exist, create it.

The database should support at minimum:

"services"

- UUID primary key
- company/workspace relationship using the project's existing architecture
- name
- category
- short_description
- description
- customer_facing_description
- requirements
- included_details
- excluded_details
- pricing_information
- availability_information
- typical_response_time
- internal_instructions
- escalation_instructions
- status
- created_at
- updated_at

Use appropriate types, constraints, indexes, and timestamps.

Do not blindly assume the company's existing ownership/RLS structure. Inspect the existing tables and follow the architecture already used by Properties, Units, Contacts, and Team/Staff.

6. Relationships

Services must use proper relational tables.

At minimum, support:

Contact ↔ Service

A contact can use multiple services and a service can have multiple contacts.

Use a junction table such as:

"contact_services"

with:

- id
- contact_id
- service_id
- relevant relationship/status information if useful
- notes if useful
- created_at
- updated_at

Do NOT store service IDs or service names as comma-separated text.

Service ↔ Staff

A service can have multiple responsible staff members and a staff member can be responsible for multiple services.

Create/use a proper junction table.

Service ↔ Property

Support associating services with properties using a proper relationship table.

Service ↔ Unit

Support unit-level service relationships where appropriate.

Use the existing "properties", "units", "contacts", and "staff" tables and their actual UUIDs.

All relationships must respect company/workspace isolation and must not allow cross-company relationships.

7. Contacts Integration

The Contacts page was already expanded to support Services.

Make sure its Services section now reads from the actual "services" and relationship tables created/used here.

Do not create a second service system.

A contact's profile should be able to display the services they use, and the Services profile should be able to display the contacts using that service.

Preserve all existing Contacts functionality.

Keep the database structure clean because the Services data will later be consumed by the FlowPoint AI.
